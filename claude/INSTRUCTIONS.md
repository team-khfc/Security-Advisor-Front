## 프로젝트

보안길잡이(영문 서비스명 **SecurityAdvisor**, 백엔드 패키지 `kr.securityadvisor`): 정보보안을 모르는 공공기관 담당자가 AI 인터뷰로 방화벽신청서·보안성검토 신청서 초안을 만드는 서비스. 서류 생성기가 아니라 현업↔전문가(정보보안·ICT인프라 담당자) 지식 중계 플랫폼. 2026 공공 AI 대전환 챌린지 세션1 출품 — 본 제출 11.11, 예선 11.13~17, 결선 11.25. 1차 범위는 서류 2종·역할 4종(일반 사용자/정보보안/ICT인프라/기관 관리자) 고정, 11.08 기능 동결. **운영 기관은 설치당 1곳 고정**: 한 설치 = 한 기관(예: 한국주택금융공사가 설치하면 운영 기관·기관 관리자는 한국주택금융공사로 고정). 여러 기관을 등록하는 구조(멀티테넌트)는 만들지 않고, **기관 테이블·엔티티도 두지 않는다**(기관명·코드는 `.env` 설정값). 다른 기관은 별도 설치해 자기 설정으로 쓴다.

처리 절차는 4단계: 작성(업로드·AI 요약·인터뷰) → 담당자 협의(INFRA가 서버·IP·포트 할당 → SECURITY 검토, 1차 범위는 INFRA 선행 고정, 할당 완료 ≠ 협의 완료) → 사용자 최종 검토(AI 최종 초안은 미확정) → 확정·관리(서류 확정 ≠ 방화벽 적용). 차수 반환(2→1, 3→2, 3→1, 4→3)은 사유 필수, 기존 값 보존 + 보완 필요 항목 강조 표시. 종결(반려)·철회 상태 있음. 한 번에 여러 서류 신청 가능 — 사업 건(BusinessCase) 1 : N 신청(SecurityRequest), 공통 정보는 사업 건에 한 번만 수집(scope=CASE), 상태·반환·제출은 신청 단위로 독립, 사업 건 상태는 계산값. 운영 도메인: 2단계 진입 시 분야별 담당자 자동 배정(검토 행위는 배정자만, 자기 신청 담당 금지), 처리 기한은 서버가 영업일로 계산(경과해도 상태 불변), 감사 이력은 추가 전용·업무와 같은 트랜잭션, 방화벽 확정 시 규칙 단위 생성(적용은 INFRA가 사람으로서 기록), 업무 지표는 읽기 전용(개인 순위 금지), 알림은 화면 안·업무 상태 불변. 상세는 FUNCTIONAL_SPEC.md.

## 작업 전 참조 순서

1. 전체 그림·확정 결정·**기준 버전 표** → PROJECT_CONTEXT.md
2. 기능 명세·도메인 맵·불변식 → FUNCTIONAL_SPEC.md
3. 개발 작업(사람·AI 공통 규칙, 명령, 구조, DDD, Git) → AGENTS.md
4. 운영(팀·범위·일정·제출 책임·문서 개정 절차) → PROJECT_RULES.md
5. 코드 작성 → CODING_STYLE.md(Google 기반) + SECURE_CODING.md(KISA 기반, 같은 비중)
6. 협업 절차·API 계약·수용 기준 → CONTRIBUTING.md
7. 화면·KRDS·접근성 → design.md / 디자인 시안은 github.com/team-khfc/prototype-soo 의 **최신본**(디자이너 작업 영역 — 아래 "디자인 시안")

저장소:

- **서버·DB 개발 → github.com/team-khfc/Security-Advisor-Back** — Spring Boot·Flyway·seed·개발용 DB compose·OpenAPI 계약 파일·ADR·용어집
- **화면 개발 → github.com/team-khfc/Security-Advisor-Front** — Next.js 화면·컴포넌트·모의 API
- **완성본·배포·제출 → github.com/team-khfc/Security-Advisor** — Back·Front 릴리스 태그의 스냅샷(`back/`·`front/`) + 전체 실행 `compose.yaml`·`.env.example`·구동안내서. 사용자는 이 저장소만 받아 `docker compose up -d --build`로 실행한다(Docker만 필요). 여기서 기능을 고치지 않는다
- 개발 작업 시작점 → github.com/team-khfc/prototype(선행 화면·도메인 검사 15종), 디자인 시안 → github.com/team-khfc/prototype-soo(디자인 담당 작업 저장소)
- Back과 Front는 서로 없이 각자 개발·테스트한다(Front는 모의 API가 기본). API 계약(OpenAPI)은 Back이 소유하고 Front는 그 계약을 따르며, 계약 변경은 Back PR이 먼저다. 한 저장소에 다른 쪽 코드를 넣지 않는다. 규칙 문서 9종과 점검 스크립트는 세 저장소 루트에 같은 버전으로 둔다.

## 디자인 시안 (디자이너 작업 영역 — 수시 변경)

- 시안은 디자이너가 언제든 고칠 수 있다. 화면 작업 직전에 prototype-soo 기본 브랜치 최신본과 `MERGE_NOTES.md`를 확인하고, 산출물(PR 설명 등)에 참고한 시안 커밋을 적는다. 기억이나 예전 사본으로 작업하지 않는다.
- 규칙 문서에는 시안의 화면 수·파일명·커밋을 고정하지 않는다. 시안이 바뀌어도 규칙 문서는 개정하지 않으며, 시각 규칙이 바뀌면 디자이너가 design.md를 개정한다.
- 우선순위: 업무 의미(단계·상태·권한) → FUNCTIONAL_SPEC.md, 시각 규칙 → design.md, 개별 화면 모양 → 최신 시안. 시안이 업무 규칙과 다르면 시안대로 구현하지 않고 디자이너·기획에 알린다.
- 시안의 동작(브라우저 저장소 데이터, 사용자 전환, CDN 라이브러리, 저장·게시·AI 버튼)은 시연용이지 구현 기준이 아니다. 시안 저장소는 디자이너만 수정하고, 다른 사람은 이슈·코멘트로 의견을 전한다.
- 11.08 기능 동결 이후의 시안 변경은 오류·접근성 수정만 팀장 승인으로 구현에 반영한다.

## 작업 전 버전 확인 (필수)

1. 작업을 시작하기 전에 PROJECT_CONTEXT.md 5장 **기준 버전 표**를 읽고, 이 지침(설정 '지침' 칸)과 참조할 문서 머리말의 버전·개정일이 표와 같은지 확인한다.
2. 다르면 **버전·개정일이 높은 쪽을 최신으로 본다**. 지침 칸이 문서보다 낮으면 문서를 따르고, 작업 결과 첫머리에 "지침 칸 vX → 최신 vY 교체 필요"를 알린다.
3. 같은 문서가 여러 곳(프로젝트·저장소·공유 문서·zip)에 있고 내용이 다르면, 임의로 하나를 골라 진행하지 말고 차이를 먼저 보고한다.
4. 문서를 개정할 때는 PROJECT_RULES.md 7-1의 **문서 개정 절차**를 따른다(머리말 버전·개정일 → 기준 버전 표 → 사본 동기화 → 지침 칸 → 팀 공지).
5. 프로젝트 문서는 문서마다 한 경로에만 둔다 — 규칙 문서는 프로젝트 루트, 이 지침은 `claude/INSTRUCTIONS.md`. 같은 이름의 사본을 다른 경로에 두지 않는다.

## 불변 원칙 (모든 산출물 — DDD의 도메인 불변식으로 코드에서 강제)

1. AI는 제안만, 확정은 항상 사람이 한다. AI 값을 확정 사실처럼 표시 금지. 3단계 AI 최종 초안의 보완분도 미확정.
2. 모든 값은 출처 4종(사용자 답변/AI 추론+근거/담당자 입력/담당자 확인)을 가진다. 출처 없으면 "담당자 확인 필요".
3. 지식(공개자료 RAG)과 사실(기관 비공개 컨텍스트·담당자)을 분리. AI가 내부 IP·시스템명을 지어내지 않는다.
4. 상태 의미 구분: 검토 완료 ≠ 실제 처리 완료, 할당 완료 ≠ 협의 완료, 서류 확정 ≠ 방화벽 적용, 초안 ≠ 게시본 ≠ 제출본.
5. 권한·업무 전이·버전 검증은 서버가 최종 판단. 클라이언트 role·기관 값 신뢰 금지(모든 계정은 운영 기관 1곳 소속).
6. 차수 반환·종결·철회는 사유 필수, 기존 값·이력 보존. 반환 시 보완 필요 항목만 강조 표시.
7. 한 신청의 상태 전이는 같은 사업 건의 다른 신청을 바꾸지 않는다. 공통 정보 변경은 미제출 신청만 재검토 표시, 제출본은 불변.

## 절대 금지

- 실제 내부 정보(내부망 IP·서버·자산·비공개 규정·실존 개인정보)를 코드·커밋·모의데이터·스크린샷·영상·문서에 넣는 것. 전부 합성 데이터만.
- 비밀값(API 키 등)의 코드·Git·DB 평문 저장. 환경변수/키 참조만.
- 실행하지 않은 검사·테스트를 통과로 보고하는 것. 미구현·미검증은 그대로 표기.
- 11.11 마감 후 공공GitLab 산출물 수정.

## 기술 스택(확정)과 방법론

Next.js(App Router)+React 19+TS 5.9+TanStack Query / **Java 25(LTS)**+Spring Boot 4.1+Gradle(Kotlin DSL)+Spring Data JPA / PostgreSQL 17+Flyway+pgvector / Docker Compose. **AI 계층은 Spring AI 2.0**(ChatClient·ChatModel, PGVector VectorStore)을 공통 LLM 어댑터 인터페이스 뒤에서 사용 — 버전 고정, 최소 범위, 업무 코드는 Spring AI 타입에 직접 의존 금지. LLM은 2종 이상 구동 입증, 연결 구성은 DB 설정 데이터로 관리(키는 환경변수 참조만, 동적 엔드포인트는 허용 목록 검증). 코딩 스타일은 Google 가이드, 보안은 KISA 시큐어코딩 가이드 준수.

**API는 RESTful로 설계한다**(상세는 AGENTS.md 5장): 경로는 `/api/<복수형-kebab-case>` 자원 명사(동사 금지), 행위는 HTTP 메서드 의미대로(GET 안전, PUT·DELETE 멱등), 상태 전이는 `status`를 직접 PATCH하지 않고 하위 자원 생성(`POST …/submissions`, `…/stage-returns`)이나 단일 하위 자원 설정(`PUT …/closure`)으로 표현해 도메인 메서드를 호출한다. 오류는 ProblemDetail로 400(형식)·401·403(권한)·404(없음·접근 권한 없는 타인 자원)·409(revision·중복)·422(업무 규칙 위반)를 구분하고, 생성은 201 + `Location`. 계약은 OpenAPI로 관리한다.

**개발 방법론은 DDD**: 기능 패키지 = 바운디드 컨텍스트(kr.securityadvisor.<컨텍스트> — request/review/document/configuration/knowledge/llm/auth/assignment/audit/policy/insight/notification/common), 코드 식별자는 유비쿼터스 언어(docs/glossary.md), 업무 규칙은 domain 계층의 애그리거트·도메인 메서드·불변식으로 강제(상태 전이는 setter가 아니라 complete()·submit() 같은 업무 동사), domain은 프레임워크 비의존. 11.11까지는 전술 패턴까지만 — 이벤트 소싱·CQRS 미도입.
