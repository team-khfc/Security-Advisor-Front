# 담당자 등록·재배정·업무 인계 화면 검증

2026-11-10. Front main `e90fcde` 기준. 시안 `prototype-soo@563dd7e76aeeb4fe63f010bec9cd1f9bac16d5dc`와 MERGE_NOTES를 확인하고 기존 폼·표·배지 스타일을 사용했다.

## 사용자 흐름

1. 기관 관리자가 계정에 ICT인프라/정보보안 역할을 부여한다.
2. 계정·담당자 관리에서 해당 분야에 등록하고 기본 담당자를 지정한다. 계정 역할과 분야 등록은 별개다.
3. 역할 변경·계정 비활성·등록 비활성 등으로 진행할 수 없는 신청은 재배정 필요 건수/목록에 표시된다. 상세에서는 분야별 사유를 보여 준다.
4. 등록된 활성 담당자 중 후임을 선택하고 사유를 남겨 인계한다. 동명이인을 구분하도록 이름과 아이디를 함께 표시한다.
5. 후임은 기존 답변과 협의 내용을 이어서 처리한다. 기본 담당자 지정은 신규 자동 배정에 사용되며 기존 신청을 자동 이동하지 않는다.

## 구현 경계

서버가 판정한 재배정 사유와 적격 여부를 사용하며 계정/등록 변경 뒤 신청·담당자·건수 캐시를 갱신한다. 관리자 전용 등록·기본 지정·등록 활성 관리 API를 연결했다. 모의 API에도 계정과 등록의 분리 및 기본 배정 규칙을 반영했다. API 계약 출처는 `contract/README.md`에 기록한다.

## 검증 결과

- `npm run format && npm run check`: 타입·린트·문서 검사 및 33개 파일/296개 테스트 통과. 담당자 등록→기본 지정→사유 있는 비활성화, 역할 변경 시 기본 지정 차단, 진행 단계/필요 분야별 인계 표시 검사를 추가했다.
- Docker 이미지 빌드·기동 성공. 실제 Back/PostgreSQL의 합성 계정 `handoff-40f5e73a-*`, 신청 261~264로 HTTP/저장 결과 27개를 확인했다.
- 브라우저에서 관리자 역할 변경·비활성화, 담당자 등록·기본 지정, 인계 목록/상세, 양 분야 재배정과 사유 이력 저장을 확인했다.
- 신규 담당자로 로그인해 신청 263의 전임자 서버 정보를 읽고 수정·저장했다. 재배정 자체로 협의 기록이 바뀌지 않는 것도 확인했다.
- 등록 비활성화 시 재배정 필요가 늘고, 재활성화 시 해소됐다. 원래 기본 담당자 `infra`/`security`를 복구했다.
- 브라우저의 실제 좁은 창(너비 487px, 문서 너비 472px)에서 페이지 가로 넘침 없이 사용했다. Tab 이동, Enter 저장, Escape 취소와 초점 복귀, 빈 사유 저장 차단을 확인했다.
- 실제 화면에서 발견한 동명이인 식별 문제와 인계 후 답변 편집 안내 문구를 수정하고 새 Docker 이미지에서 재확인했다.

기존 DB·저장 파일과 합성 검증 기록은 보존했다. 실제 장비·외부 AI·외부 알림은 사용하지 않았다. 이 PR은 기능 브랜치 배포 검증이며 main 병합은 별도다.
