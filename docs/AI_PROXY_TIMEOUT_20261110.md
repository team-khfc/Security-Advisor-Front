# AI 요청 대기 제한 수정 (2026-11-10)

## 원인과 정책

기존 중계는 모든 백엔드 요청을 30초에 중단했다. 브라우저의 로그인 세션 만료가 아니라 서버 간 요청 제한 문제이며, 백엔드의 세션 기본값 30분과 별개다. 모델 구성은 최대 600초까지 허용하므로 90초나 180초로 설정한 모델도 기존 중계에서 먼저 끊길 수 있었다.

`lib/aiProxy.ts`에서 요청 방식과 정확한 경로에 따라 제한을 적용한다.

| 요청 | 중계 제한 |
| --- | --- |
| 인터뷰, 항목 제안, 최종 초안, 담당자 질의, 서류 유형 제안 | 660초 |
| 기획서 분석 반영 (서류 2종 순차 AI 호출) | 1,320초 |
| 모델 연결 시험 (백엔드 최대 30초) | 45초 |
| 일반 조회·저장 및 비동기 분석 접수 | 30초 |

긴 요청에는 Node HTTP/HTTPS 전송을 사용하여 fetch의 별도 헤더 대기 제한에 의해 다시 잘리지 않게 한다. 명시적 제한과 호출자 취소 신호를 함께 적용하며 자동 재시도와 리다이렉트는 하지 않는다. 쿠키·CSRF·요청 본문·응답 상태·복수 Set-Cookie 전달은 유지한다. 실제 401은 그대로 전달한다.

추가 프록시나 게이트웨이가 있는 배포에서는 해당 경로의 응답 대기 제한도 이 정책 이상이어야 한다. 시간 초과나 화면 이탈이 백엔드 작업의 취소·롤백을 보장하지 않으므로 결과·이력을 먼저 확인하도록 안내한다. 추후 더 많은 순차 호출이 필요하면 제한을 계속 늘리는 대신 비동기 작업·진행 상태 조회로 전환해야 한다.

## 검증

- `npm run check`: 포맷·타입·린트·문서 검사 및 테스트 330개 통과.
- `docker build`: 실제 운영 빌드 통과.
- 별도 도커 프론트와 합성 지연 서버: AI POST의 35초 응답 정상 전달, 일반 GET의 30초 제한 및 504, 실제 401 전달 확인.
- 자동 검사: 긴 요청 제한 도달 시 504, 재시도 없음, 쿠키·CSRF·본문·응답 쿠키·취소 신호 유지.
- 실제 모델의 속도나 품질 평가는 아니며, 기존 데이터·모델 설정은 변경하지 않는다.
