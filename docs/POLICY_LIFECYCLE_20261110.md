# 확정 방화벽 규칙 흐름 검증

2026-11-10 · Front 이슈 #36

## 발견과 수정

Front main `92a47047ad455443117a33c26bee2f61ab176137`에서 `/policies`가 구현 예정 안내만 표시했다. Back main `b3eca56560d24af73142bf198a7ad74d69c93f88`의 규칙 목록·적용·회수·연장 API가 이미 구현돼 있었으므로 계약 변경 없이 화면을 연결했다.

- ICT인프라: 적용 완료(메모), 적용 불가(필수 사유), 회수(필수 사유)를 명시적으로 선택·확인·저장한다.
- 신청자: 자기 규칙을 조회하고 적용된 규칙을 참조하는 새 연장 신청을 만든다. 진행 중 연장은 기존 신청 링크로 이어간다.
- 정보보안 담당자·관리자: 기록 조회. 신청자·관리자 메뉴와 확정 신청 상세에서 정책 목록으로 이동할 수 있다.
- 한국어 상태, 서버 기준 건수·거르기, 읽기 전용 통신 정보, 처리자·시각·메모·사유와 원 신청 이력을 표시한다. `appliedAt`은 회수 시 갱신되는 계약이므로 화면에서 **최근 상태 기록**으로 표시한다. 최초 적용 시각은 신청의 감사 이력에서 확인한다.
- 저장 중 중복 실행, 오류 시 입력 소실, revision 충돌 시 무조건 재시도를 막는다. 최신 상태를 명시적으로 다시 읽어야 저장할 수 있다.
- 실제 브라우저에서 발견한 Escape 후 초점 손실을 수정했다. 좁은 화면에서는 표 안에서만 가로 이동하며 대화상자 날짜 입력은 한 열로 배치한다.
- 모의 API에도 확정 제출본 기반 규칙과 동일한 역할·사유·revision·연장 중복 검사를 연결했다.

## 실제 도커 사용자 흐름

Front `http://127.0.0.1:3001` → Spring Boot·PostgreSQL 연동. **합성 데이터만 사용했고 실제 장비는 변경하지 않았다.** 아래 업무 저장은 브라우저 화면에서 수행했다.

| 합성 대상 | 확인 결과 |

| 사업 15 / 신청 25 / 확정 제출본 7 / 규칙 2 | ICT인프라가 적용 완료 메모를 저장하고 다시 열어 처리자·시각·메모 확인 |

| 원 신청 이력 | 적용 완료·연장 생성·회수 세 사건과 회수 사유를 실제 화면에서 확인 |
| 키보드·좁은 화면 | Enter로 열기/저장, Tab·Space로 확인, 대화상자 안 Tab 순환, Escape 후 원 버튼 초점 복귀. 390×844에서 페이지 가로 넘침 없음 |

API 재조회로 규칙의 출발지·목적지·프로토콜·포트·기간·제출본 참조가 점검 전과 동일하고, 원 신청 24·25가 계속 확정 상태임을 비교했다. 감사 기록 394(적용), 402(연장), 404(회수)를 확인했다. 신청자와 정보보안 담당자의 합성 회수 저장 요청은 모두 403으로 거부됐다.

연장 **신청 생성·작성으로의 연결**까지 점검했다. 새 신청 28의 재협의·제출·확정은 이번 점검에서 진행하지 않았으며 작성 중으로 보존했다. 만료 예정·만료의 실제 날짜 경과나 실제 장비 적용은 시험하지 않았다.
